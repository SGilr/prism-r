### The manifest defect

`pipeline/build.py` wrote `data/processed/manifest.json` unconditionally,
before checking the exit code. A build that failed part way overwrote the
committed provenance record with the steps it had managed to run.

The dangerous part is that the wreckage did not look like wreckage. The
`outputs` list is built from what exists on disk rather than from what the run
produced, so it still named all 28 processed files with correct checksums. Only
`steps` was truncated, from 13 to 1. The file read as a valid manifest of a
build that had inexplicably skipped twelve steps. A run narrowed by `--only` or
`--from` degraded it the same way.

`manifest.json` is now written only when every step ran and every gate passed.
Anything else writes `manifest.partial.json`, git-ignored, carrying
`build_complete: false`. Two tests hold the invariant. The previous check
tested step names as a subset of the expected order, which a one-step manifest
satisfies, and that is why nothing caught it.

The history of `manifest.json` was audited afterwards. Step counts across every
committed version run 7, 7, 7, 8, 9, 10, 10, 11, 12, 13, 13, rising as steps
were added and each matching its commit's scope. **No truncated manifest ever
reached the repository**, so no published provenance was affected. That is why
this is not in the corrections section of `methods.md`, which is for defects in
published figures.

The build aborts at step 4 of 13, so nothing downstream runs. Nothing depends

section asks readers to judge the work rather than take it on trust, that is
the load-bearing claim.

### The trap that was fixed first

Re-cutting the bundle before `720dd92` would have published the four boundary
files with the wrong provenance. `SOURCES` in `make_raw_bundle.py` matches by
longest directory prefix, and `geo/` was a directory-wide entry written for the
ONS authority-codes FOI spreadsheet. The four geojson files would have been
listed in `RAW_BUNDLE.md` as:

> ONS lookup table for UK authority codes 2024 (FOI-2024-2008), retrieved 2026-05-17

Wrong source, wrong URL, wrong date, stated confidently in the document a
reader uses to verify the inputs against the publishers. `geo/boundaries-2023`
now has its own entry dated 2026-09-03, and the catch-all is narrowed to the
one file it describes. `geo/` mixes three ONS retrievals, unlike the
per-publisher directories, so a bare prefix there silently attributes anything
added later. `tests/test_raw_bundle.py` holds all three points.

### A decision before publishing

`make_raw_bundle.py` generates the tag `raw-data-2026-09`, which already
exists, so `gh release create` will refuse.

- **Replace the asset in place** with `gh release upload raw-data-2026-09 <file> --clobber`. Keeps the tag the docs and CI already name, but changes what a published, citable asset contains under an unchanged name, which probably wants a line in the corrections section.
- **Publish a new tag** and leave the old one standing. CI and `refresh.yml` select the newest `raw-data-*` automatically, so both keep working.

The second is more consistent with the corrections culture: nothing published
gets quietly rewritten.

## 4. Finding, now fixed

**The suppression tests did not detect an unsuppressed sub-threshold count.**

Running the smoke test executes `pipeline/build.py`. Suppression is a stage
that runs after the ingest steps, so when the build aborts at step 4, the three
ingest steps that succeeded have already written their **pre-suppression**
output to `data/processed/`. The working copy is then holding values that
disclosure control exists to withhold.

Concretely, after the failed build, `data/processed/remand_outcomes.json` held
three records with a count below six and `"suppressed": false`, including
`count: 5` for Unknown ethnicity, `rlaa` remand, 2025. Rule 1 of the disclosure
standard is that counts below six are suppressed.

**The full suite passed 113 tests in that state**, and the 26 tests in
`tests/test_suppression.py` passed on their own against it. The structural
guard added on 3 September asserts that records *marked* suppressed retain no
recoverable field. It does not assert the converse, that no unmarked record
carries a count below the threshold.

Nothing was committed and nothing was published: the file was restored with
`git checkout` and the tree is clean. The exposure was local to a working copy
for a few minutes. But the guard against committing it is currently the fact
that a failed build is noisy, not a test.

Fixed in `tests/test_suppression.py` as
`test_no_published_count_sits_below_the_primary_threshold`. It reads every
processed output and fails if any record left unmarked carries a count between
1 and 5, counting a field named `count` or `*_count`, and the `value` and
`numerator` of a context indicator whose code names it a count, such as
`lac_count` and `arrest_count`. A count of exactly 0 is a true zero and is
left alone, matching `pipeline/suppress.py`.

It was verified against the real regression rather than a synthetic one: the
exposed record was reintroduced, the new guard failed on it and named the
cell, and the other 26 suppression tests passed in that same state. Restored
afterwards, and the tree is clean.
